# Shared UI & shadcn

`apps/web/src/shared/ui` holds AMCore's UI primitives — generated by the
[shadcn](https://ui.shadcn.com) CLI, hand-customized where noted, or written
directly for AMCore where shadcn has no equivalent. This page is the reuse
rule, the safe operating procedure for the CLI, and the reasons behind both —
written after a live CLI run found regressions neither research nor review
predicted. Full deliberation, including the spike transcript, lives in the
maintainer-only `ai/models-talk.md` (Track 5) if you need the _why_ in more
depth than this page carries.

## Reuse-first rule

In this order, every time a UI need comes up:

1. **Use what's already in `@/shared/ui`.** Check the inventory below before
   writing new markup.
2. **`shadcn add` a primitive that doesn't exist yet** — following the
   procedure below, never a bare `shadcn add` against the live tree.
3. **Write a local abstraction only when reuse is real** — a pattern used in
   two or more places, not a guess at future need. A one-off composition
   belongs in the feature/view that needs it, not in `shared/ui`.

`shared/ui` is imported per-module (`@/shared/ui/button`), never through a
barrel — see
[Boundaries & guardrails § `shared` is a collection of modules](./fsd-boundaries-and-guardrails.md#shared-is-a-collection-of-modules)
for why.

## Base UI, not Radix

`apps/web/components.json`'s `style` is `base-nova` — components generated
from here on come from [Base UI](https://base-ui.com), not Radix Primitives.
This was a live decision, not a default accepted on faith:

- shadcn's own July 2026 changelog made Base UI the default for new
  projects; Radix remains supported, not deprecated.
- AMCore's Radix footprint before this decision was two near-stock files
  (`button.tsx`, `label.tsx`) — the cheapest point to switch was before more
  primitives were built on either library.
- A scratch-worktree spike (below) produced the actual API deltas this
  decision rests on: Base UI's `render` prop instead of Radix's `asChild`;
  a standalone `label` registry item independent of any `Field` composition;
  an upstream CLI warning that switching libraries can require manual
  updates outside `shared/ui`.

**Not every file has been migrated yet.** `form.tsx`, `alert.tsx`, `card.tsx`,
and `input.tsx` are still on the Radix-era shadcn generation — migrate them
opportunistically, the next time one of them needs a real customization, not
as a standalone sweep.

### Radix packages still installed

`@radix-ui/react-label` and `@radix-ui/react-slot` remain in
`apps/web/package.json` even though `button.tsx`/`label.tsx` no longer use
them — `form.tsx` still does (`FormLabel`'s prop type, `FormControl`'s
`Slot`). Before removing either package, confirm with:

```bash
rg '@radix-ui' apps/web/src
```

Remove a package only once this returns nothing.

## The CLI is not safe to run against the live tree

A scratch-worktree spike (`shadcn init -b base -p nova --reinstall -y -f`
against a disposable `git worktree`, never `main`) found regressions that no
amount of reading the CLI's own docs predicted:

- **It silently rewrote AMCore's deliberately distinguishable chart colors
  to five shades of the same gray**, directly contradicting a comment in
  `globals.css` promising "distinguishable hues, independent of the neutral
  primary." No warning in the CLI output.
- **It broke `--font-sans`** into a self-referencing, unresolvable variable
  (`--font-sans: var(--font-sans)`), silently falling back to the browser
  default font.
- **A file named `spinner.tsx`** — AMCore's own hand-written component, not
  a shadcn generate when it was written — collided with shadcn's now-official
  `Spinner` registry item and was queued for silent overwrite, which would
  have dropped its `size` prop entirely.

None of this shipped — it was caught in a disposable worktree, never against
`main`. But it means the CLI's own `--dry-run`/interactive prompts are not
enough protection by themselves. Follow this procedure every time:

### 1. Scratch-worktree first, always

```bash
git worktree add ../amcore-<task>-spike -b spike/<task> main
cd ../amcore-<task>-spike/apps/web && pnpm install --frozen-lockfile
```

Run whatever `shadcn add`/`init` command you're evaluating **here**, never in
the real working tree. Read the generated output, decide what to hand-port,
then delete the worktree:

```bash
cd /path/to/AMCore && git worktree remove ../amcore-<task>-spike --force
git branch -D spike/<task>
```

### 2. Hand-port file by file

Copy only what you decided to keep into the real repo, preserving every
existing customization (extra button sizes, `data-variant`/`data-size`,
the destructive-foreground token, `cursor-pointer` — check the
[inventory](#current-inventory) for what each file already carries). Do not
run `shadcn init -f`/`--reinstall` against the live tree to "sync" —
that is exactly the command that produced the chart-color and font
regressions above.

### 3. Inspection flags are safe; the real invocation is not

`--dry-run`, `--diff`, and `--view` all write nothing — verified directly
(`git status` was empty after each, in a disposable worktree):

```bash
pnpm exec shadcn add <component> --dry-run   # preview only, writes nothing
pnpm exec shadcn add <component> --diff      # shows the diff, writes nothing
pnpm exec shadcn add <component> --view      # shows file contents, writes nothing
```

**The real invocation (no inspection flag) is different: a declined
interactive overwrite prompt still mutates `package.json` and the lockfile.**
Dependency installation happens before the per-file overwrite prompt, so
even answering "no" to every file leaves dependency changes in place:

```bash
$ echo "n" | pnpm exec shadcn add button
...
✔ Installing dependencies.          # already happened
? The file button.tsx already exists. Would you like to overwrite? … no
```

After any real invocation — including one where you declined every file —
run `git status`/`git diff` and revert anything you didn't mean to change.
Use `--dry-run`/`--diff`/`--view` for inspection; only drop to the real
invocation once you've decided what to keep.

### Protected files: check before every run

`spinner.tsx` and `api-error-alert.tsx` are AMCore-owned, not shadcn
generates. **If either name ever appears in a `shadcn add`/`--reinstall`
write list, stop and hand-port or skip it** — do not confirm the overwrite.
Filename collision with an upstream registry addition (as happened with
`spinner.tsx`) is exactly the failure mode a general "check the customized
files" rule misses; these two are named explicitly for that reason.

`button.tsx` isn't on this list but deserves the same care: some registry
items (`alert-dialog`, at least) declare it as a dependency and try to
regenerate it. Always check the write list before confirming.

## Token changes stay surgical

`globals.css`'s color tokens are governed by
[Brand, theme & tokens](./brand-theme-and-tokens.md) and Track 2's WCAG AA
contrast test suite (`apps/web/src/shared/lib/theme.test.ts`). A shadcn
preset switch touches this file wholesale — see the chart-color and
`--font-sans` regressions above. When a token genuinely needs to change:

1. Add or edit only the specific token, never let a CLI run rewrite the
   whole generated block.
2. Run the contrast suite:
   ```bash
   pnpm --filter web test:run -- src/shared/lib/theme.test.ts
   ```
3. If you're adding a new `-foreground` pairing (as `--destructive-foreground`
   was, closing a real gap where every other semantic color already had one),
   add it to the `pairs` array in that same test file so future changes are
   checked automatically, not just once by hand.

`theme.test.ts` also carries a permanent regression guard pinning
`--chart-1` through `--chart-5` and `--font-sans` to their exact current
values — proven to actually fail (not vacuous) by reproducing the CLI's
exact regression against it before it shipped. If you deliberately change
either, update the guard in the same PR and explain why in the commit.

## Hardcoded copy still slips in

`shared/ui` has no business meaning and owns no message-catalogue keys — but
that doesn't make it exempt from AMCore's "never inline user-facing text"
rule (see [i18n & errors](./i18n-and-errors.md)). A shadcn-generated `Dialog`
hardcoded the English string `"Close"` as its built-in close icon's
screen-reader label; it was caught in review, not by any automated guard.

The fix pattern: **require the caller to supply translated text as a prop**,
rather than `shared/ui` importing `next-intl` or owning a key itself.
`DialogContent` now types this as a discriminated union so it's enforced at
compile time, not just by convention:

```tsx
type DialogContentProps = DialogPrimitive.Popup.Props &
  ({ showCloseButton?: true; closeLabel: string } | { showCloseButton: false; closeLabel?: never })
```

A caller passes `closeLabel={t('common.close')}`; `shared/ui` never sees a
literal string. Apply the same pattern to any future shadcn port whose
generated output bakes in visible or screen-reader-only English text — check
every new primitive for this before it ships, the same way you'd check it
for hardcoded English anywhere else in `apps/web`.

## If generated code fails lint

Treat shadcn output as upstream reference code, not as automatically
AMCore-ready code. AMCore's frontend contract is stricter than shadcn's
general-purpose registry, so a freshly generated file may fail lint or review
for valid reasons:

- raw Tailwind palette classes (`bg-red-500`, `dark:text-gray-800`) must become
  semantic tokens (`bg-destructive`, `text-muted-foreground`);
- inline `style` must be replaced with classes, a CSS Module, or a reviewed
  one-line `eslint-disable` only for a genuinely dynamic value;
- hardcoded user-facing English, including `sr-only` labels, must move to the
  caller as translated props or children;
- imports must follow FSD paths (`@/shared/ui/button`, feature public APIs,
  locale-aware navigation), even if the generated example uses a different
  shape.

Do **not** accept a shadcn component by disabling lint just because the CLI
generated it. A scoped `eslint-disable` is a last-resort exception with a
reason, visible in review; it is not the normal path for importing registry
code into the starter. If the generated code needs a color that has no
semantic token yet, either choose an existing token or make a surgical token
change using the procedure above.

## Testing convention

Vitest + React Testing Library, matching the existing pattern in
`button.test.tsx`/`skeleton.test.tsx`/`dialog.test.tsx`: render the
component, assert on `data-slot`/`data-variant` attributes and behavior
(click, open/close, variant switching), not implementation detail. No
Storybook yet — that's a separate, dedicated track.

## Sidebar and Toast: deliberately not here yet

Two primitives from shadcn's catalog are **not** in `shared/ui`, on purpose:

- **Sidebar** — the low-level primitive was deferred entirely to the starter
  cleanup track, which owns the `(dashboard)/layout.tsx` route-thinness fix
  it would compose into. Building an unused app-shell API ahead of that
  work risked guessing a shape the real nav/locale/auth requirements would
  contradict.
- **Toast** — deferred to the API-client/query-patterns track. No mutation
  flow exists anywhere in `apps/web` yet (form submissions currently surface
  errors through `api-error-alert.tsx`, not a toast); adding Sonner with
  nothing to trigger it would be speculative. When it's picked up, add it
  citing shadcn's current Sonner docs directly — Base UI does ship its own
  stable Toast primitive, so "Base UI has no Toast" is not valid reasoning
  for the choice.
